1. 定义与边界

  • LLM agent：以 LLM 作为策略，在“观察→推理→动作（工具/API/GUI）”的循环中运行的系统，带有跨步状态。
  • 工具增强型 LLM（tool-augmented LLM）：单次或少次调用工具，没有自主循环和长期状态。
  • Agentic workflow：由开发者预先编排的固定流程，LLM 只在节点上做决策。
  • 传统 MAS / 自主 agent：BDI、强化学习等非 LLM 体系，只作为对照。
  • 企业式工作流：多步骤、有状态、跨工具或跨角色的业务任务。
  • 可复现分级：
    • R3：任务、环境、评测脚本全部公开，可本地或 Docker 重跑
    • R2：数据和代码公开，但依赖闭源 API 或商业实例（如 ServiceNow、Salesforce）
    • R1：只公开数据或 trace
    • R0：不公开
    • 无法确认时标“未核实”。

3b. 领域详解：各方向在研究什么、具体贡献是什么

本节内容依据各论文的 arXiv 摘要（2026-10-23 通过 arXiv API 获取，原文存于 research/abs/abs.json）。数字都直接取自摘要。“我的解读”段落是推断，不是论文的结论。

领域 1：企业工作流基准——“agent 到底能做多少真实工作？”

核心问题：从”会不会调用 API”转向”能否在有状态、多应用、有规则约束的业务环境里把事情做完”。 主要研究路线：①仿真公司或业务系统；②真实 SaaS 平台；③办公软件或桌面；④软件工程。

论文 环境与规模 主要发现 / 贡献
TheAgentCompany（Xu et al.，NeurIPS’25 D&B） 自托管的”小软件公司”：内部网站、数据、模拟同事；agent 可以浏览网页、写代码、和同事沟通 最强 agent 自主完成 30% 的任务；简单任务可以自动化，长时程任务仍做不到。代码、数据、环境全部公开
τ-bench（Yao et al.，ICLR’25） 零售、航空客服；LLM 模拟用户 + 领域 API + 策略文档 用”对话结束时的数据库状态 vs 目标状态”做评测；提出 pass^k（k 次都成功）。GPT-4o 成功率 <50%，零售域 pass^8 <25%，说明 agent 很不稳定
τ²-bench（Barres et al.，ICML’26） 新增电信 dual-control 域（用户也要操作设备），建模为 Dec-POMDP 从”没有用户”切换到”双方都要操作”时性能大幅下降；能分开统计推理错误和沟通/协调错误；带组合式任务生成器
AppWorld（Trivedi et al.，ACL’24 最佳资源） 9 个日常 app、457 个 API、约 100 个虚拟用户；750 个任务 用基于状态的单元测试评测，允许多种解法，同时检查 collateral damage（附带破坏）。GPT-4o 普通任务约 49%，挑战任务约 30%
WorkArena / WorkArena++（ServiceNow） 真实 ServiceNow 平台；第一代 33 个任务 → 第二代 682 个工作流 第一代同时推出 BrowserGym，开源和闭源模型差距明显；第二代考察规划、算术推理、检索，并能自动生成大量 ground-truth 轨迹用于微调
CRMArena / Pro（Salesforce） 16 类 CRM 对象，含潜变量（如投诉习惯、违规）；Pro 版有 19 个任务，覆盖 B2B/B2C 第一代：ReAct <40%，函数调用 <55%。Pro：单轮约 58%，多轮降到约 35%；agent 几乎没有保密意识，靠提示改善保密又会损害任务表现
OSWorld（NeurIPS’24 D&B） 真实操作系统（Ubuntu/Windows/macOS），369 个跨应用任务 人类 72.36%，最佳模型 12.24%；主要卡在 GUI grounding（定位界面元素）和操作知识
OfficeBench / OdysseyBench Office 多应用；Odyssey 有 602 个长时程任务（Word/Excel/PDF/邮件/日历） OfficeBench：GPT-4o 47%，失败主要来自冗余操作、幻觉、应用切换。Odyssey：需要从很长的交互历史中提取信息，并提出 HomerAgents 自动造题
SWE-Bench Pro 1,865 题，41 个仓库，含商业私有仓库 抗数据污染；任务需要专业工程师花数小时到数天；对失败轨迹做了失败模式聚类

我的解读：这些基准反复指向三类共性短板——多轮/人机交互（τ²、CRMArena-Pro）、规则遵循（τ、CRMArena）、长时程状态保持（TheAgentCompany、Odyssey）。另外，“单次成功率”会高估真实可用性。

领域 2：失败分类与失败归因——“它为什么失败？是谁、在哪一步出的错？”

核心问题：不只是报一个成功率，而是把失败拆解到原因。演进路线如下： 人工建分类法 → 标注数据集 → 用 LLM 自动归因 → 训练专门的归因模型 → 用干预来验证归因。

论文 方法 贡献 / 数字
MAST（Cemri et al.，NeurIPS’25 D&B） 对 150 条 trace 做 grounded theory 建分类法，再用 LLM-judge 扩展标注 14 种失败模式、3 大类（系统设计、agent 间失配、任务验证）；1,600+ 条标注 trace，覆盖 7 个框架；κ=0.88。结论：多 agent 系统（MAS）的收益常常很小，很多失败源于系统设计而不是模型本身
Who&When（Zhang et al.，ICML’25） 定义”自动失败归因”任务；127 个 MAS 的失败日志 最好的方法：找出责任 agent 53.5%，定位错误步骤 14.2%；o1、R1 也达不到实用水平
AgenTracer（ICLR’26） 用反事实重放 + 程序化故障注入自动造标注数据（TracerTraj），再用 RL 训练 8B 归因模型 在 Who&When 上比 Gemini-2.5-Pro、Claude-4-Sonnet 高至多 18%；把归因结果反馈给 MetaGPT 等，带来 4.8–14.2% 的提升
DoVer（ICLR’26） 指出两点：只看日志的归因无法验证，“单一步骤归因”本身常常定义不当（多种修改都能修好）。改用主动干预（改消息、改计划）检验假设 18–28% 的失败试次被翻转为成功；验证或否定了 30–60% 的假设
WebSuite 把 web 任务拆成原子动作分类法 任务失败可以直接归因到具体的 web 动作
Code agent 轨迹研究（Majgaonkar et al.） 比较 OpenHands、SWE-agent、Prometheus 的成功与失败轨迹 失败轨迹更长、方差更大；72–81% 的失败轨迹其实找对了文件，成败取决于修改是否”大致正确”
Characterizing Faults in Agentic AI 从 40 个仓库的 13,602 个 issue/PR 中分层抽样 385 个故障，用 grounded theory 分析 34 种故障类型；根因包括 schema 不匹配、依赖漂移、状态管理、模型接口不稳定；145 名从业者验证。这是工程视角的分类
AgentOps 对现有 AgentOps 工具做系统映射研究 列出 agent 全生命周期中应该追踪的工件和数据，作为可观测性的参考模板

分歧与张力：Who&When 和 AgenTracer 把”准确定位到单一 agent 和步骤”当作目标；DoVer 认为这个目标常常不成立，应改用”能否修复”来评测。这是一个开放的方法论争议，也适合拿来做研究切入点。

领域 3：工具调用失败——“参数填错、读错返回值、调错工具”

论文 内容
Butterfly Effects in Toolchains（Findings EMNLP’25） 建立了 5 类参数失败分类，并用 15 种输入扰动做实验：参数名幻觉主要源于 LLM 本身的局限，其余失败主要由输入来源（用户指令、工具返回等）引起。建议标准化工具返回格式、改进错误反馈、保证参数一致
ToolScan 定义 7 种 tool-use 错误模式，并为每种构造测试；主流 LLM 都会出现这些错误
Characterizing Faults（见上） 工程侧证据：结构化输出解析和 schema 不匹配是高频根因

领域 4：歧义、澄清与”能力边界意识”

论文 内容
Learning to Ask（EMNLP’25） 分析真实用户指令，构建 NoisyToolBench。发现 LLM 因 next-token 训练目标会编造缺失的参数；提出 Ask-when-Needed（AwN），并用 ToolEvaluator 自动评估准确率和效率
CAR-bench（ACL’26） 车载助手场景，58 个工具。设计了 Hallucination 任务（缺工具或缺信息时是否承认）和 Disambiguation 任务。前沿推理模型在消歧任务上的稳定通过率 <50%，主要原因是过早行动；还会为了满足用户而违反策略或编造信息
ASPI（预印本，摘要未获取） GS 标题显示：主动澄清会放大提示注入风险。这说明”多澄清”并不是免费的，与安全领域有交叉

领域 5：安全——提示注入、权限、记忆投毒

攻击与评测 - InjecAgent（Findings ACL’24）：1,054 个用例，17 个用户工具、62 个攻击工具。攻击意图分为直接伤害和窃取数据两类。ReAct-GPT-4 有 24% 的概率中招，加入”hacking prompt”后成功率接近翻倍。 - AgentDojo（NeurIPS’24 D&B）：97 个任务（邮件、网银、旅行），629 个安全用例。它不是静态测试集，而是可扩展的攻防环境。 - Adaptive Attacks（Findings NAACL’25）：测试了 8 种防御，用自适应攻击全部绕过，攻击成功率 >50%。结论：防御论文必须用自适应攻击来评测。 - AgentPoison（NeurIPS’24）：通过优化后门触发器来投毒长期记忆或 RAG 知识库。投毒率 <0.1%，攻击成功率 >80%，对正常任务的影响 <1%。 - MemoryGraft（预印本）：把恶意的”成功经验”植入经验记忆，利用 agent 模仿过去成功做法的倾向，造成跨会话的持久行为漂移。这对”自我改进型 agent”是新的攻击面。

防御（从”检测”到”按设计保证安全”） - Task Shield（ACL’25）：把安全问题重新表述为任务对齐，即每个动作都要服务于用户目标。在 AgentDojo 上，GPT-4o 的攻击成功率降到 2.07%，任务效用 69.79%。 - CaMeL（预印本，Google DeepMind/ETH）：从可信的用户查询中提取控制流和数据流，不可信数据无法改变程序流；再用 capability 机制阻止数据外泄。可证明安全的前提下解决 77% 的任务，无防御时是 84%。 - AgentSpec（ICSE’26）：一种 DSL，规则由”触发器 + 谓词 + 执行动作”组成，在运行时强制执行。代码 agent 中 >90% 的不安全执行被阻止，开销在毫秒级；还尝试用 o1 自动生成规则。 - Progent（预印本）：可编程的权限控制。本轮没有拿到摘要，细节待补。

安全行为评测（不局限于注入） - ToolEmu（ICLR’24）：用 LM 模拟工具执行来低成本发现高风险失败。经人工验证，68.8% 的失败是真实有效的；最安全的 agent 也有 23.9% 的情况出现风险行为。 - ST-WebAgentBench（ICLR’26）：222 个企业 web 任务，每个都配有策略。提出 CuP（Completion under Policy，遵守策略的完成率）：CuP 不到名义完成率的 2/3。 - OpenAgentSafety（ICLR’26）：使用真实工具（浏览器、bash、文件系统、消息平台），350+ 个多轮、多用户任务。在易出安全问题的任务中，不安全行为占 51.2%（Claude-3.7）到 72.7%（o3-mini）。 - Agent-SafetyBench：2,000 个用例，没有一个 agent 的安全分超过 60%。主要缺陷是缺乏鲁棒性和缺乏风险意识；只靠防御提示不够。 - Contextual Integrity（Google）：把”隐私”定义为信息流是否符合语境，用于引导 agent 的表单填写行为。

结论差异：AgentDojo 的检测器在非自适应攻击下能把攻击成功率降到约 8%，但会被自适应攻击打穿。Task Shield 报告 2.07%，但这是非自适应设置下的数字，需要和 Adaptive Attacks 那篇对照着看。CaMeL 一类”系统设计型”防御更难被绕过，代价是效用下降和工程复杂度上升。（我的解读）

领域 6：可靠性、“假成功”与成本

论文 内容
CLEAR（预印本） 分析了 12 个基准：同等精度下成本相差 50 倍；单次 60% → 8 次一致 25%。只优化准确率得到的 agent 贵 4.4–10.8 倍。15 名专家评估：CLEAR 与生产成功的相关 ρ=0.83，只看准确率时 ρ=0.41
ReliabilityBench（预印本） 三个维度：一致性 pass^k、语义扰动 ε、故障注入 λ（超时、限流、部分响应、schema 漂移）。扰动让成功率从 96.9% 降到 88.1%；限流伤害最大；ReAct 比 Reflexion 更稳
Procedure-Aware Evaluation / Corrupt Success（预印本） 在 τ-bench 上，27–78% 的”成功”其实是腐败成功，即结果对了但过程违规；加入过程门控后排名改变；还暴露了基准本身的缺陷（模拟器伪影、矛盾的奖励信号）
SWE-PRM（预印本） 推理时用过程奖励模型中途纠偏（循环、冗余探索、不停止）。SWE-bench Verified 从 40.0% 提升到 50.6%，额外成本低至 $0.2
Efficient Agents（预印本） 在 GAIA 上用 cost-of-pass 分析：保留 OWL 96.7% 的性能，成本从 $0.398 降到 $0.228

我的解读：这一组论文共同说明，“成功率”这个指标本身就是失败来源之一。它掩盖了不一致、违规过程和成本，企业落地的评测应该是多维的。

各领域之间怎么连起来（读者导航）

  • 基准（领域 1）提供失败样本 → 分类与归因（领域 2）解释原因 → 工具、澄清、安全（领域 3–5）是具体失败机制及其防御 → 可靠性评测（领域 6）检验修好没有。
  • 交叉热点：
    • 澄清 × 注入（ASPI）
    • 保密意识 × 效用（CRMArena-Pro）
    • 记忆 × 安全（AgentPoison、MemoryGraft）
    • 归因 × 修复（AgenTracer、DoVer）
