0. 问题定义

ReHAC 一类工作研究的是 when：agent 在哪一步该请人介入。本文研究的是 whom：在多个用户共用一个 agent 的企业场景里，每个人的角色、权限、知识和成本都不同，agent 求助时应该找哪一个人。

用户提出的设想是：whom 的决策应该建立在一个显式的角色定义系统之上。

把问题拆开，“找谁”这个决策依赖四类信息：

维度 含义 举例
知识（Knowledge） 谁知道这条信息 HR 经理知道各部门的设备需求
权限（Authority） 谁有权批准或决定 财务总监批准预算
可用性与成本（Availability/Cost） 谁有空、打扰谁的代价最高 打扰 CTO 的代价高于打扰工程师
可信度（Reliability） 谁给的答案更可能正确 一线工程师对细节的了解可能比经理准确

1. 有没有论文做过？结论：没有发现完全覆盖这个问题的论文；相邻方向各做了一部分

1A. 最接近的四条线

方向 代表工作 已经做到的 缺少的
多专家延迟决策（Multi-expert Learning to Defer, L2D）（ML 理论方向） DeCCaF（arXiv 2403.06906）；Top-k L2D（ICLR 2026，arXiv 2504.12988）；Two-stage multi-expert L2D（NeurIPS 2023）；PiCCE（arXiv 2602.17144） 学习把每个样本分给哪一位专家，同时考虑专家各自的准确率、成本和工作量上限。DeCCaF 在欺诈检测场景中模拟了 9 名风控分析员，误分类成本平均降低 8.4%。Top-k 一次可以问 k 位专家。PiCCE 指出，在专家很多时，“该信任哪位专家”这件事本身很难学，会导致欠拟合 这些方法针对单步分类，而不是多步 agent 工作流；专家只用“准确率向量”来刻画，没有角色、权限、组织结构；也不涉及对话
自适应群体问询 Whom to Query for What（ICML 2026，arXiv 2602.14279） LLM agent 同时选择问什么、问谁，在预算约束下进行。用 LLM 估计每个问题的期望信息增益，再用异构图神经网络利用参与者的属性来选人 目标是估计群体意见（问卷调查），不是完成工作任务；把人看作同质的“受访者”，没有区分角色和权限
多用户 LLM agent Multi-User LLM Agents（arXiv 2604.08567）；Harness-MU（arXiv 2606.21856）；Collaborative Memory（arXiv 2505.18279）；PrincipalBench（arXiv 2606.30383）；GroupMemBench 把“一个 agent 服务多个用户”形式化为多委托人决策问题，用户之间有不同的角色、偏好、权限等级；Harness-MU 用执行钩子强制执行“谁有权限、谁的指令优先”；Collaborative Memory 用二部图表示“用户—agent—资源”的访问控制 研究的是被动方向：多个人向 agent 发指令时，agent 该听谁的、哪些信息不能泄露。没有研究主动方向：agent 卡住时该去找谁
Agent 内部的路由与澄清 AgentAsk（ACL 2026）；MasRouter（ACL 2025）；AgentRouter 在多 agent 系统里，学习在哪条消息传递的边上发起澄清、把子任务路由给哪个 agent；AgentAsk 训练时同时权衡澄清的成本、延迟和准确率 路由的对象是 agent 或模型，不是人；不涉及人的组织角色

1B. 其他相关但更远的工作

  • 企业环境基准里已经有“人”和“角色”：
    • TheAgentCompany 有 17 个模拟同事，每人有职位、职责和所在频道；agent 必须自己判断该联系谁（详见 §2）。
    • EnterpriseBench（EMNLP 2025，arXiv 2510.27287）建模了访问控制层级和跨部门工作流，500 个任务，最强模型的完成率是 41.8%。
    • 但这两个基准都没有把“找谁”作为单独的评测维度。
  • 企业升级与分流：
    • 银行欺诈分流 agent（arXiv 2605.16268）通过对话把客户路由到正确的专家团队，分类准确率提升 30.6%。不过它路由的是客户，不是 agent 自己求助。
    • ⚠️ 阿里客服现场实验（arXiv 2605.14830）、工业值班（on-call）多 agent 系统（ASE 2025）：只看到标题，没有读到摘要。
  • 社区问答里的专家发现与问题路由：传统 IR 方向，把问题推送给最可能会答的人。它提供了“找谁”的经典方法，比如用人的话题画像和社交关系来匹配，但不涉及 agent。

1C. 结论

  • “在多步企业任务中，agent 主动求助时，基于显式的角色和权限模型选择找哪个人”这一组合，在本轮检索中没有找到直接对应的论文。
  • 这个结论只说明本轮没找到，不等于确定不存在。检索覆盖 Google Scholar 前 10 条结果、12 个检索式，可能有遗漏，尤其是 2026 年下半年的预印本。投稿前需要再做一次针对性检索。
  • 新颖性风险评估：
    • 方向的组合较新，风险中低。
    • 但每个组件都有前人工作，至少需要和以下三类做对比：
      • 多专家 L2D：怎么选专家；
      • Multi-User LLM Agents / Harness-MU：怎么建模角色和权限；
      • ReHAC：何时请人介入。

3. 建议的研究框架（这是研究设计，不是已有结论）

3.1 形式化

  • 在 ReHAC 的 MDP 基础上，把动作空间从“agent 或人”扩展为“agent，或 人₁ … 人ₙ”。
  • 每个人 hᵢ 有一个角色档案：
    • Rᵢ = ⟨知识域 Kᵢ，权限 Aᵢ，成本 cᵢ，可用性 vᵢ，可信度 ρᵢ⟩
    • 来源：从组织架构、职责描述、历史交互中构建。
  • 奖励：

R=T−∑tλ⋅cht−μ⋅𝟙[越权或泄露]R = T - \sum_t \lambda \cdot c_{h_t} - \mu \cdot \mathbb{1}[\text{越权或泄露}]

  • 也就是说，要在任务成功、打扰谁的成本、权限违规三者之间权衡。

3.2 三个可检验的研究问题

  1. 显式角色模型有没有用？ 对比三种设置：
    • 无角色信息：agent 只知道人名；
    • 只有自然语言职责描述，即 TheAgentCompany 现有的设置；
    • 结构化角色档案，即本文提出的框架。
  2. 结构化角色档案能不能从数据中学出来？ 比如从历史问答记录中推断谁掌握什么知识。这对应信息检索里的专家发现。
  3. when 和 whom 要不要联合决策？ 对比两种做法：
    • 先决定是否求助，再决定找谁（两阶段）；
    • 一个策略同时输出“是否求助”和“找谁”。

3.3 实验方案

步骤 做法 成本
① 诊断性研究（最便宜，可以先做） 在 TheAgentCompany 公开的约 1.9k 条轨迹上，标注每次 agent 联系 NPC 的情况：问对人 / 问错人 / 该问没问 / 不该问却问了。统计“找错人”在失败案例中占多大比例 不需要算力，主要是标注；可以用 LLM 预标注加人工抽检
② 基准构建 扩展 TheAgentCompany 的 NPC 场景：给每个任务设置多个可能的求助对象（干扰项、有权限但不知情的人、知情但没有权限的人），并为打扰每个人设定成本 中：需要写场景和评测器
③ 方法对比 基线包括：随机选人；LLM 读职责描述后自行判断（prompt 方法）；多专家 L2D 改写版；ReHAC 扩展到多人动作空间；本文提出的“角色档案 + 学习”方法 中高：训练 7B 级别的策略模型，参考 ReHAC 的规模
④ 真人验证（可选） 小规模真人扮演角色，参照 ReHAC 的 14 人设置 招募成本

指标： - 任务成功率； - 首次求助命中率（是否第一次就问对了人）； - 总打扰成本； - 越权或泄露次数； - 求助轮数。

可投稿的 venue： - 偏方法和基准：ACL / EMNLP / NeurIPS D&B； - 偏人机交互和组织：CHI / CSCW。

4. 风险与难点

  • 模拟人的真实性：NPC 由 LLM 扮演，被打扰的成本是人为设定的，可能和真实组织差别很大。
  • 角色信息从哪来：真实企业的组织架构和职责数据涉及隐私，很难公开；论文只能用合成组织。
  • 和 Multi-User LLM Agents、Harness-MU 撞题的风险：它们已经在做多用户的角色和权限建模，2026 年可能很快出现“主动求助”方向的后续工作，需要持续跟踪。
  • TheAgentCompany 中真正依赖“找人”的任务大约只有 41 个（带 scenarios.json 的任务），规模偏小，需要扩充。
