# Study 4 控制器：来自论文分析一侧的建议（2026-11-11）

读了 `research/study4/` 的 README、训练过程、诊断、评测和 trace 后的建议。按优先级排列，每条写明理由和可执行的检查。
这些是建议，不是已验证结论；是否执行、预算多少由研究者决定。

## 先说结论

现在的失败主要不是"模型太小"或"训练不够久"，而是三个更上游的问题叠在一起：

1. **标签不对**：模仿的是教师的实际动作（教师 dev 自己只有 9/16 成功），且 83% 是"拿到信息之后继续干活"的 NO_ASK，真正关键的 ASK 只有 38 条、分散在 15 个人身上。
2. **训练基本没学动**：LoRA lr=1e-5、87 步，train NLL 还有 0.95，accuracy 刚好等于"永远 NO"。这是欠拟合，不是过拟合。
3. **评测被执行器接口污染**：SELF 模式下 mini 反复 post、不 submit，完整交付 4/16→0/16，这和控制器学没学会无关。

建议先用很便宜的方式确认"控制器理论上能带来多少收益"，再决定要不要继续训练。

## 建议 1（最高优先级）：先跑一个 oracle 控制器，测上限

用 gold dependency graph 写一个规则控制器（不训练）：在每个决策点，如果存在"前置已满足、但自己还没拿到"的步骤，就 ASK 该步骤的 admissible 联系人；否则 NO_ASK。执行器和 NPC 保持现在的 mini 不变，跑同样 16 dev（或更多）。

- **理由**：这告诉你"完美的 when + whom 决策"配上 mini 执行器最多能到多少。论文数据显示：只要问了，第一次找对人的比例是 79/79，失败主要来自**被拒后不补救**和**问的时候没带上前一步拿到的值**（见 TribalBench 论文 §5.3 和 Figure 5 的工资任务对比）。如果 oracle 控制器 + mini 依然完成不了，瓶颈就在执行器写请求/处理拒绝，而不在控制器，训练控制器帮不上忙。
- **Go/no-go**：oracle 臂相对原生 mini 的提升 = 控制器能贡献的天花板。天花板很小就先别训练。
- **成本**：16 题 × 1 次 mini 调用，和现在一次评测同量级。

## 建议 2：用 gold DAG 直接生成 oracle 标签，替代"模仿教师"

TribalBench 每个任务都有 gold DAG，所以每个公开状态下"该不该问、该问谁"可以确定性地算出来（只用于构造标签，不进入控制器输入）。

- 在训练任务的每个状态：有"就绪且未满足"的步骤 → 标签 = ASK(该步骤的 admissible 联系人之一)；否则 NO_ASK。被拒绝后的状态也能算（步骤仍未满足 → 再问同一人，并要求带上缺的上下文）。
- 这比 NEXT_STEPS 里 P2 的"受控分支执行"便宜得多，而且标签是正确的，不会复制教师的错误。P2 可以留到之后验证"oracle 标签在真实执行中是否真的更好"。
- 可以从**所有已有轨迹的状态**（4 个模型的 R1 + 补跑，几百个 episode）生成标签，不只是 GPT 教师的 59 条，数据量和状态多样性都会大很多。注意按任务分组切分，避免泄漏。

## 建议 3：减少决策次数，解决类别不平衡

现在每个 cycle 都做一次决策，导致大量"已经拿到信息、继续写文件"的 NO_ASK 淹没了关键状态。

- **只在关键决策点问控制器**：任务开始时、收到 NPC 回复之后、以及准备写交付物/submit 之前。其它步骤直接交给执行器。
- 或者保留每步决策，但在 loss 里按类别/阶段重新加权（如 ASK 权重 ×4–5），并报告 ASK recall、balanced accuracy，而不是 overall accuracy。

## 建议 4：先证明模型"学得会"

- **lr 太低**：LoRA rank 8 常用 lr 是 1e-4 到 2e-4，1e-5 基本动不了。先在 20–30 条训练状态上做过拟合 sanity：能把这些状态背下来（ASK recall 接近 1）再谈泛化。
- **动作表示**：现在是对整个 action JSON + EOS 的 log-prob 求和，长度不同的标签（NO_ASK 8 token，Chen Xinyi 12 token）天然有偏。改成分类头，或给每个动作分配一个等长的单 token ID（如 A0…A16）。诊断里已经列了，建议直接做，不必再做大量消融。
- **对齐目标**：控制器公开输入里写的是 T−0.15C，评测用的是 R，权重不一致。论文最终版用的是 R = T − 0.05·max(0, C−C\*) − 0.3·N_auth − 0.1·N_waste（只罚超出最省力路径的打扰），建议两边都统一成这个，见 `tribalbench/scorer/scorer.py`。

## 建议 5：先修执行器接口（同意 NEXT_STEPS 的 P0）

SFT 臂完整交付 0/16 的主要原因是 SELF 模式下 mini 反复 post、不 submit。在修好之前，任何控制器比较都不公平。

- 两臂用完全相同的普通工具 schema、进度提示和终止约定。
- 加一个两臂共享的公共进度提示（"交付文件已写入 / 摘要已发布"），不依赖 gold。
- 先用 mock 回放验证，再上真实调用。

## 建议 6：扩大控制器的动作，覆盖"被拒后补救"

论文发现，会问的模型主要失败在"被拒后放弃"，而且成功的一半以上都经历过一次拒绝再补救（GPT-5.4 的 21 次成功里 16 次）。现在控制器只决定 ASK(person)，问题内容完全交给执行器。

- 考虑把动作改成 ASK(person, step)，执行器写请求时由系统自动附上该步骤所需、且已经拿到的值（这些值来自公开对话历史，不是 gold）。
- 或者在执行器的 ASK 提示里加一句固定规则："引用你之前从同事那里拿到的所有相关数值和编号"。这一条成本几乎为零，可以先单独测。

## 建议 7：训练与评测的成本

- **NPC 用规则代替 LLM**：每个任务的 `npc_scenarios.json` 里已经写了释放规则（需要的上下文、前置步骤）。训练/采样阶段可以用确定性规则 NPC（检查请求里是否包含 required_context、前置是否满足），不用调 API，可以无限采样；评测时再用 LLM NPC。这样后面做 RL（如 GRPO）也负担得起。
- **评测集太小**：16 dev 已经用来选 checkpoint。建议对 60 个任务做按任务家族分组的 k-fold 交叉验证，或者用已有的任务生成器再造一批新任务作为封存测试集。

## 推荐顺序

| 步骤 | 内容 | 大致成本 |
|---|---|---|
| 1 | Oracle 控制器上限测试（建议 1）+ 执行器"引用已获数值"规则（建议 6 第二条） | 两次 16 题评测 |
| 2 | 修执行器接口（建议 5） | 本地实现 + mock |
| 3 | 用 gold DAG 生成 oracle 标签，扩充到所有已有轨迹状态（建议 2）| 本地，零 API |
| 4 | 新 SFT：分类头 / 等长 action ID、lr 1e-4、类别加权、先过拟合 sanity（建议 3、4）| 免费 Colab 级别 |
| 5 | 规则 NPC 上做 RL，奖励用论文的 R（建议 7）| 本地为主 |

第 1 步的结果决定后面是否值得做：如果 oracle 控制器都带不来明显收益，应该把研究重心放到执行器（请求怎么写、被拒后怎么补救），而不是控制器。
