# Study 1 Execution Design: Help-Seeking Failures in Real Agent Trajectories (RQ1)

> Draft 2026-10-23. Corresponds to RQ1 / H1a–H1c in the proposal. Pilot code: `research/pilot/parse.py`, `rq1.py`. Pilot results: `03_Feasibility_Pilot_*.md`.
> Items marked "to verify" still need to be checked in the data.

## 0. Question this study answers
**RQ1**: In real enterprise tasks, how often do current LLM agents fail because of help-seeking errors, and what kinds of errors do different models make?

- **H1a (prevalence)**: Among failed tasks, a substantial share involves at least one help-seeking error.
- **H1b (model differences)**: The distribution of error types (wrong person / omitted / no follow-up) differs across models.
- **H1c (association)**: Help-seeking errors are associated with lower task completion. This holds at the trajectory level and also at the checkpoint level within a trajectory.

This is an **observational study**. We do not run new agents; we analyze public trajectories that already exist.

## 2. Formal definitions (mathematical basis)

### 2.1 Basic objects
- Colleague set $\mathcal{U}$, with $|\mathcal{U}| = 17$.
- Task $\tau$. For each task we derive the following from `scenarios.json` and `task.md`:
  - **Required set** $N_\tau \subseteq \mathcal{U}$: people who must be contacted to complete the task.
  - **Admissible set** $A_\tau \supseteq N_\tau$: people it is reasonable to contact but not required. For example, in hr-pick-interviewer-2, asking Mark and Jessica one by one before Emily is a valid path.
  - **Order constraint** $\prec_\tau$ (optional): e.g., "ask Chen Xinyi for the list first, then contact the people on it."
  - **Checkpoint mapping** $\kappa_\tau: \text{checkpoint} \to 2^{\mathcal{U}}$: which people's information each checkpoint depends on.
- Trajectory $\xi_{\tau,m}$: the run of model $m$ on task $\tau$, i.e., a sequence of events $(e_1, \dots, e_T)$.

### 2.2 Help-seeking events
A help-seeking event is a tuple
$$h = (t,\; u,\; \text{msg},\; \text{reply},\; \text{channel})$$
where $t$ is the step, $u \in \mathcal{U}$ is the recipient, and channel is a DM or an @mention in a channel.
**Detection rule**: in the observation, the room header is `# first_last` (a direct message) and the next action contains a send (`fill` + `Enter`); or a channel message contains `@first_last` (the rule already implemented in the pilot).

Contact set: $C_\xi = \{u : \exists h \in \xi,\; h.u = u\}$.

### 2.3 Event-level labels (one label per event)
| Label | Definition | How it is determined |
|---|---|---|
| `correct` | $u \in N_\tau$ and the request matches what $u$ knows | Rule + LLM judge |
| `admissible` | $u \in A_\tau \setminus N_\tau$ | Rule |
| `wrong_person` | $u \notin A_\tau$ | Rule |
| `redundant` | The same person was asked again for the same information after already answering | LLM judge |
| `no_follow_up` | $u \in N_\tau$ and $u$ replied, but the key information in the reply was never used in later actions or the final output | LLM judge (compare the reply with later actions and the final file) |

### 2.4 Trajectory-level variables
- **Coverage**: $\text{cov}(\xi) = \dfrac{|C_\xi \cap N_\tau|}{|N_\tau|} \in [0,1]$
- **Omission count**: $n_{\text{miss}} = |N_\tau \setminus C_\xi|$
- **Wrong-person count**: $n_{\text{wrong}} = |C_\xi \setminus A_\tau|$
- **Help-seeking error indicator**: $E(\xi) = \mathbb{1}[n_{\text{miss}} > 0 \;\lor\; n_{\text{wrong}} > 0 \;\lor\; \exists\, \text{no\_follow\_up}]$
- **Reachability (exclusion variable)**: $\text{reach}(\xi) = \mathbb{1}[\text{the agent reached any chat page}]$. The pilot found 37% of trajectories never reached the chat page. Their failures are unrelated to help-seeking, so the main analysis excludes them.
- **Task-text naming**: $\text{named}_\tau = \mathbb{1}[N_\tau \text{ is written explicitly in task.md}]$ (24/40 tasks are named). This variable separates "failed to follow instructions" from "failed to choose the right person."
- **Outcomes**: checkpoint score $s(\xi) \in [0,1]$ (from eval.json); success $y(\xi) = \mathbb{1}[s = 1]$.

## 3. Execution steps

| Step | Input | Process | Output file |
|---|---|---|---|
| **A. Task specification** (manual, one-time) | task.md, scenarios.json, checkpoints | For each of the 40 tasks, fill in $N_\tau$, $A_\tau$, $\prec_\tau$, $\kappa_\tau$, $\text{named}_\tau$. **Two people label independently, then reconcile** | `task_spec.csv` |
| **B. Event extraction** (deterministic script) | trajectories json.gz | Parse into a sequence of help-seeking events with reply text | `events.jsonl` (one line per event) |
| **C. Automatic labeling** | events + task_spec | Rules handle correct / admissible / wrong; an LLM judge (fixed prompt, temperature 0) handles redundant / no_follow_up | `labels.jsonl` |
| **D. Human audit** | Stratified sample | Stratify by model × trajectory category and sample about 80 trajectories (2 per task). Two annotators label independently using the codebook | `audit.csv`, inter-annotator agreement |
| **E. Aggregation and statistics** | labels + scores | Section 4 | Tables, figures, regression results |

**Codebook**: one page that gives the definition, a positive example, and a counterexample for each of the five labels, plus edge-case rules (e.g., asking the right person a vague question counts as `correct` but is marked low quality).

## 4. Analysis methods

### 4.1 Annotation reliability
- Cohen's kappa:
$$\kappa = \frac{p_o - p_e}{1 - p_e}$$
where $p_o$ is observed agreement and $p_e$ is chance agreement.
- Report two values: human vs. human (target ≥ 0.7), and LLM judge vs. human consensus (target ≥ 0.6).
- If the LLM judge falls below target, revise the prompt, or label that category fully by hand.

### 4.2 H1a: prevalence
- Estimate $\hat p = P(E = 1 \mid y = 0,\ \text{reach} = 1)$.
- Confidence interval: trajectories from the same task are correlated, so use a **cluster bootstrap resampled by task** (1,000 resamples) rather than the plain binomial interval. Report the Wilson interval alongside for reference.
- Report each error type separately: omitted / wrong person / no follow-up / redundant.

### 4.3 H1b: model differences
- Contingency table: model (10) × error type (4).
- Test: every model ran the same tasks, so observations are not independent. Use a **permutation test stratified by task**: within each task, shuffle model labels and recompute the χ² statistic. Report Cramér's V as the effect size:
$$V = \sqrt{\frac{\chi^2}{n(k-1)}}$$
- Figure: per-model coverage vs. success rate scatter, plus stacked error-type bars.

### 4.4 H1c: association (two levels)

**Trajectory level: mixed-effects logistic regression**
$$\operatorname{logit} P(y_{\tau m} = 1) = \beta_0 + \beta_1\,\text{cov}_{\tau m} + \beta_2\,n^{\text{wrong}}_{\tau m} + \beta_3\,\text{named}_\tau + \beta_4 \log(\text{steps}_{\tau m}) + \gamma_m + u_\tau$$
- $\gamma_m$: model fixed effect, which absorbs differences in overall model capability.
- $u_\tau \sim \mathcal{N}(0, \sigma^2)$: task random effect, which absorbs differences in task difficulty.
- Report the odds ratio $e^{\beta_1}$ with 95% CI. As a robustness check, swap the outcome to a linear mixed model on score $s$.

**Checkpoint level: within-trajectory comparison (stronger evidence)**
- For each checkpoint $c$ and the person set $\kappa_\tau(c)$ it depends on, compute
$$\Delta = P(c\ \text{passed} \mid \kappa_\tau(c) \subseteq C_\xi) - P(c\ \text{passed} \mid \kappa_\tau(c) \not\subseteq C_\xi)$$
- Compare only different checkpoints within the same trajectory. This controls for that run's model and task, and comes closer to "missing this person's information caused this checkpoint to fail."
- Test: McNemar's test, or a conditional logistic regression stratified by trajectory.

**Interpretation caveat**: this is still an association, not a causal effect. An agent that asks the right people may simply be more capable overall. The model fixed effects and the checkpoint-level design reduce this confounding but do not remove it. Causal evidence comes from the interventional experiments in Study 2.

### 4.5 Secondary analysis
- **named vs. not named**: compare omission rates across the two task types. If the omission rate rises sharply when names are not given, that suggests failures come from choosing whom to ask, not from failing to follow instructions. This motivates Study 2.

## 7. Validity threats

| Threat | Mitigation |
|---|---|
| Contact detection misses or misfires (UI changes, search-then-send patterns) | Human audit; report detection precision and recall |
| UI failures (37%) confounded with help-seeking failures | Main analysis restricted to reach = 1; full data reported as a supplement |
| Trajectories are from Dec 2024 (OpenHands 0.14), older models | State this as a limitation; Study 2 uses current models |
| One trajectory per model per task, so no within-model repeats | Treat as one sample; use bootstrap and mixed models for correlation |
| Defining $N_\tau$ / $A_\tau$ involves judgment | Two independent annotators; report agreement |
| Some tasks use a CEO/NPC "helper" style, so there is little choice over whom to ask | Use the named variable for stratified analysis |
